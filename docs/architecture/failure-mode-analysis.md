# Failure Mode Analysis

## Scope

This table documents expected behavior and recovery intent for known failure scenarios in Milestone 2 architecture.

| # | Scenario | User-visible behavior | Authoritative state | Retry policy | Idempotency behavior | Reconciliation | Evidence | Alert |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | PostgreSQL unavailable | Service degrades, mutations fail fast with retryable error, reads may be partial via cache | No mutation commits accepted | API retries via client guidance | No idempotent side effects without commit | Fail-fast; operator instructed to retry | API/job error logs + tenant ID + command ID | Critical |
| 2 | Redis unavailable | Realtime degraded, reads still possible from DB; writes continue for some flows | DB remains source of truth | API retry for lock/cache misses | Idempotency keys can degrade to DB-only checks | Rebuild lock state from DB | Cache miss telemetry + API retry counters | High |
| 3 | Job queue unavailable | Asynchronous effects delayed; synchronous operations return acknowledged queue state where possible | DB authoritative state remains | Worker-level backoff while unavailable | Idempotency for queued operations preserved in API response cache | Re-run queue and dead-letter recovery | Job queue backlog metric | High |
| 4 | WebSocket gateway unavailable | Mutations still work via API; clients use snapshots + polling | API remains authoritative | Client reconnect retries | Replayed WebSocket messages ignored if not deduped | Clients force snapshot refresh | Websocket fail gauge and snapshot-fallback count | Medium |
| 5 | Android network loss | Customer/operator cannot submit mutations; read-only cache remains | Cached-only mode per client guidance | Client retries after restore | Client submits same idempotency key on resume | Conflict recovery using revision | Client-side network diagnostics + API conflict logs | Low |
| 6 | Browser network loss | Browser status updates stop, actions blocked | API/DB unchanged | Automatic reconnect with backoff | Retry idempotent operations on reconnect | Full snapshot on resume | Snapshot fallback counts | Medium |
| 7 | Stripe unavailable | Existing subscriptions continue, no new charge confirmation | Entitlement unchanged without successful webhook | Retry webhook processing with exponential delay | Webhook dedupe protects replays | Reconciliation job once available | Billing drift metric | High |
| 8 | Twilio unavailable | Queue SMS may be delayed or blocked by policy depending on location state | SMS ledger unchanged until send success/failure confirmed | Worker retries with policy caps | Message idempotency prevents duplicate sends | Message reconciliation after restore | Twilio send failure logs | High |
| 9 | Duplicate Stripe webhook | Second delivery ignored by inbox dedupe | Event applied once | No extra retries needed | Replay check by provider event ID | Event stream idempotent | Dedup metric | Medium |
|10| Duplicate Twilio webhook | Replay ignored with idempotency check | Message side effect remains once | No operator action needed | Provider event ID dedupe | Reprocess to verify status alignment | Provider duplicate metric | Medium |
|11| Out-of-order provider events | Later state takes precedence with explicit `event_sequence` | Ledger corrected using sequence rules | Reconciliation job for late events | Idempotent updates by normalized event hash | Audit includes ordering resolution | Event order anomaly metric | Medium |
|12| Simultaneous “Call Next” | Single terminal entry moved to CALLED; other callers see conflict | Queue state serialized by lock | User receives conflict and retries | idempotent call request returns winner result | Audit contains lock owner and conflict events | Conflict telemetry | High |
|13| Stale manual reorder | Reorder rejected if revision mismatch | No ordering mutation | Client retries with latest snapshot | Conflict returns current revision | Snapshot resync and reorder replay | Conflict logs and out-of-date warnings | Medium |
|14| Billing-cycle close partially succeeds | Cycle closes but provider reconciliation pending | Billing states marked provisional until verification complete | Retry close/reconcile job until success | Duplicate close prevented by period key | Reconcile with provider snapshots | Billing close mismatch alert | Critical |
|15| SMS send succeeds but local acknowledgement fails | Queue UI may show retry/uncertain state; later status auto-corrects | SMS ledger marks pending until provider callback | Retry acknowledgement via webhook/inbox | send idempotency prevents duplicates | Poll or webhook reconciliation job | Provider callback mismatch warnings | Medium |
|16| Number provisioning succeeds at provider but local transaction fails | Number remains unassigned until rollback path completes | Local state remains not provisioned | Job retries until consistency achieved | Request dedupe by provisioning intent ID | Reconcile mapping between provider and local tables | Reconciliation report | High |
|17| Trial reaches 100 segments during concurrent sends | Further trial sends blocked; queue operations continue | Trial SMS allowance flag set in authoritative state | Retries from same clients produce expected conflict or delay | Send idempotency prevents duplicate send charges | Counter reconciliation job checks provider event count | Trial allowance alert | High |
|18| Overage limit reached during concurrent sends | New sends are rejected once cap hit unless override exists | SMS entitlement becomes restricted in location state | Retry allowed after cap change or end-of-cycle reset | Send command dedupe ensures deterministic rejection | Recompute cap in ledger reconciliation | Overage cap exceeded alerts | High |
|19| Entitlement expires while customers remain queued | Existing customers can keep private status; no new queue entries accepted | Entitlement check blocks queue admission | No retry for admissions while expired | Idempotent repeat admission failures cached | Queue status reconciliation continues | Entitlement expiry audit event | High |
|20| Staff role revoked while device connected | Device actions become unauthorized; visible permission errors | Authorization layer rejects subsequent commands | Reconnect/reauth on next command | Stale actions return explicit scope error | Session invalidation and revalidation | Permission denial log with actor/session | Medium |
