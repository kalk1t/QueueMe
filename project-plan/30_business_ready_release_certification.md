# Milestone 30 — Business-Ready Release Certification

## Metadata

- **Estimated focused effort:** 10 working days
- **Dependencies:** Milestone 29
- **Release:** Business-Ready Version 1
- **Status:** Not started

## 1. Objective

Complete owner/admin operations, privacy, security, observability, load testing, pilot validation, Google Play closed release, and production launch certification.

## 2. Business reason

Release 1 serves real businesses and handles personal data, payments, queue operations, and SMS costs. Production readiness requires operational evidence beyond completed feature code.

## 3. Starting repository state

Before implementation:

1. Confirm every dependency milestone is accepted, not merely coded.
2. Record the current branch, commit, working-tree status, test status, and deployed environment status.
3. Read `00_locked_product_baseline.md` and verify that this milestone does not change approved product behavior.
4. Identify existing code, migrations, documentation, and provider resources relevant to this milestone.
5. Create a short pre-implementation inventory in the milestone completion report.

## 4. In scope

- Finish owner and administrator portals.
- Implement 30-day anonymization/deletion workflows, account deletion, legal pages, support processes, audits, backups, alerts, incident response, and load tests.
- Run pilot businesses.
- Prepare and execute Google Play closed testing.
- Provision production and perform launch checklist.

## 5. Explicitly out of scope

- Deferred product features
- Guaranteed public Play approval date
- Formal legal opinion generated by software team

## 6. Required deliverables

- Owner portal completion
- Admin portal completion
- Privacy/terms/SMS pages
- Retention jobs
- Security assessment
- Observability dashboards
- Backup restore report
- Load report
- Pilot report
- Play listing and closed test
- Production runbooks
- Release 1.0 evidence bundle

## 7. Architecture and implementation requirements

- Production matches approved deployment architecture and uses separate credentials/data from staging.
- All release-critical jobs and webhooks are observable and replay-safe.

General requirements:

- Preserve strict organization and location tenant isolation.
- Keep server-side authorization and entitlement checks authoritative.
- Use idempotency for retried commands, jobs, webhooks, and billing operations.
- Record audit evidence for security-sensitive, billing-sensitive, and queue-order-sensitive actions.
- Do not hide external/manual blockers behind a successful code build.

## 8. Database and data-lifecycle changes

- 30-day anonymization of name, phone, and identifiable custom answers; preserve lawful aggregate and financial/audit evidence.
- Account deletion workflow and retention exceptions documented.

Every schema change must include:

- Forward migration.
- Rollback or documented non-destructive recovery strategy.
- Index and constraint review.
- Tenant-ownership review.
- Retention and deletion classification.
- Seed or fixture updates when relevant.

## 9. API and event-contract changes

- Complete owner/admin diagnostics, exports allowed by policy, deletion requests, and health/readiness endpoints.

API requirements:

- Version contracts when a breaking change is unavoidable.
- Validate all input server-side.
- Return stable machine-readable error codes.
- Add idempotency keys to retryable mutations where relevant.
- Document WebSocket, background-job, and provider-event behavior.

## 10. Android changes

- Final signing, release build, Data Safety alignment, account deletion path, store assets, closed-test fixes.

## 11. Web changes

- Complete marketing, signup, billing, owner, admin, customer, terms, privacy, SMS terms, deletion, and support pages.

## 12. Infrastructure and operations changes

- Production environment, WAF/rate limits, alarms, dashboards, backups, restore, scaling, cost controls, and on-call routing.

## 13. Security and privacy requirements

- Threat-model closure, authorization matrix, dependency/secret scans, webhook tests, tenant isolation, token revocation, administrator audit, incident plan, and external review where appropriate.

Also verify:

- No secret, access token, payment credential, or provider credential enters source control or logs.
- Cross-tenant access is denied and tested.
- Personal data collection remains within the locked baseline.
- Customer phone numbers are not repurposed for marketing.
- Audit records are immutable or tamper-evident within the application’s trust model.

## 14. Automated tests

- Full end-to-end test suite.
- Billing test clocks for monthly and annual plans.
- SMS allowance/overage reconciliation.
- 50+ active-location scenario, hundreds of Android connections, 1,000 customer status connections target, concurrent Call Next, webhook replay, job failure, restart, and retention jobs.
- Backup restoration and disaster exercise.

Minimum quality gate:

- Existing tests remain green.
- New behavior has unit and integration coverage appropriate to its risk.
- Failure, retry, duplicate, and unauthorized paths are tested where relevant.
- Tests run in CI and locally with exact commands recorded.

## 15. Manual verification

- Recruit and support at least two barbershops and two salons.
- Run real operating days.
- Verify consent and messages.
- Review legal texts with qualified counsel.
- Complete Play Console declarations and closed test.
- Approve production launch.

Manual verification must record:

- Date and environment.
- Tester.
- Exact steps.
- Expected and actual result.
- Screenshots, logs, provider records, or other evidence when useful.

## 16. Observability

Add or update, as relevant:

- Structured logs with correlation identifiers.
- Metrics for success, failure, latency, retries, and limits.
- Alerts for release-critical failure modes.
- Administrator diagnostics that do not expose secrets or unrelated tenant data.
- Runbook steps for common failures.

## 17. Migration and rollback

Before deployment, document:

1. Deployment order.
2. Required environment variables and secrets.
3. Database migration order.
4. Compatibility with the currently deployed Android and web clients.
5. Rollback trigger conditions.
6. Rollback or forward-fix procedure.
7. Data-reconciliation steps after partial provider or billing failure.

## 18. Required documentation

Update all relevant:

- Architecture decisions.
- API contracts.
- Database dictionary.
- Environment setup.
- Operator and administrator runbooks.
- Business-owner help text.
- Privacy, consent, billing, or support text affected by this milestone.

## 19. Acceptance criteria

- At least two pilot businesses complete real operating days successfully.
- Monthly renewal, annual renewal model, monthly SMS billing, included segments, overage, and spending limits reconcile.
- Multiple Android devices operate one queue without corruption.
- Backup restoration succeeds.
- No severity-1 or severity-2 defects remain.
- Privacy, deletion, retention, support, and incident procedures are operational.
- Production release is approved for the intended distribution channel.

The milestone must not be marked complete until every criterion has direct evidence.

## 20. Completion evidence

- Release evidence index
- Pilot sign-off
- Billing reconciliation
- Security report
- Load report
- Backup restore report
- Play closed-test evidence
- Production checklist
- Tagged release and checksums

The final completion report must also include:

- Commit hashes.
- Clean working-tree confirmation.
- CI run links or identifiers.
- Test commands and exact pass/fail counts.
- Remaining manual or external blockers.
- Explicit final status: `COMPLETE`, `BLOCKED`, or `INCOMPLETE`.
